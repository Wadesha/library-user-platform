# 产品需求文档（PRD）
## 图书馆用户研究与服务平台

> 版本：v1.0  
> 编写日期：2026-08-06  
> 状态：原型验证阶段

---

## 1. 产品概述

### 1.1 产品定位

「图书馆用户研究与服务平台」是一套面向图书馆运营方与服务设计团队的**数据洞察与决策支持原型产品**。它以用户研究方法论为基础，通过可视化仪表盘、用户画像、痛点地图、需求雷达和协作空间规划，帮助图书馆回答三个核心问题：

1. **谁在用图书馆？** — 识别异质化的用户群体
2. **他们要什么？** — 理解不同群体的真实需求与痛点
3. **我们该怎么做？** — 制定可落地的服务改进与持续建设规划

### 1.2 核心价值主张

| 为谁解决问题 | 解决什么问题 | 带来哪些价值 |
|-------------|------------|------------|
| 图书馆管理者 | 缺乏系统性的用户洞察，决策靠经验 | 用数据支撑空间、资源、服务优化决策 |
| 学科馆员/服务人员 | 不清楚用户真实痛点，被动响应 | 提前识别高频问题，变被动服务为主动服务 |
| 空间/设施规划者 | 不知道空间使用冷热分布 | 优化布局、开放时间、设施配置 |
| 用户研究团队 | 调研方法零散，结果难沉淀 | 建立标准化调研工具库与长期画像体系 |

### 1.3 产品边界

- **本产品原型不替代**图书馆集成管理系统（ILS）、门禁系统、数据库统计系统。
- **本产品原型定位为**：这些系统的数据消费层 + 用户研究方法论的知识库 + 服务改进的规划协同层。

## 2. 目标用户与使用场景

### 2.1 目标用户角色

| 角色 | 主要职责 | 典型使用场景 |
|------|---------|------------|
| **图书馆馆长/主任** | 战略规划与资源配置 | 查看满意度趋势、痛点分布，制定年度服务重点 |
| **服务主管** | 日常运营优化 | 关注占座、噪音、设施等高频反馈，跟踪改进效果 |
| **学科馆员** | 学科服务与咨询 | 查看研究型用户需求，设计嵌入式信息素养培训 |
| **空间规划者** | 空间改造与设施配置 | 查看热力图，决定是否需要增设静音舱或研讨间 |
| **活动策划者** | 阅读推广与社群运营 | 了解休闲型/体验型用户偏好，策划活动 |
| **用户研究员/学生团队** | 调研执行与分析 | 调用问卷框架、方法库，输出用户画像报告 |

### 2.2 关键场景（User Story）

1. **场景 A：年度服务规划**  
   作为馆长，我希望看到过去四个季度的满意度趋势和痛点分布，从而决定下一年度预算投向「数据库校外访问优化」还是「研讨间隔音改造」。

2. **场景 B：空间改造决策**  
   作为空间主管，我希望查看各楼层各时段的拥挤热力图，判断自习区是否足够、是否需要把部分低频藏书区改造成静音舱。

3. **场景 C：精准服务触达**  
   作为学科馆员，我希望了解研究型用户在「文献检索」和「跨学科资源」上的痛点，从而设计一场针对性的信息素养工作坊。

4. **场景 D：协作社群孵化**  
   作为活动策划者，我希望看到合作型用户的未被满足需求（学伴匹配、知识共享平台），从而发起跨学科读书会并匹配合适空间。

5. **场景 E：调研快速启动**  
   作为用户研究员，我希望复用一套标准化的问卷维度和访谈提纲，在一周内启动一次针对新生用户的研究。

## 3. 功能需求

### 3.1 功能架构

```
图书馆用户研究与服务平台
├── 数据层
│   ├── 用户调研问卷数据
│   ├── 业务系统日志（门禁/借阅/预约/数据库）
│   └── 定性研究记录（访谈/焦点小组/观察）
├── 分析层
│   ├── 用户分群模型（7 类 Persona）
│   ├── 需求强度模型（7 维度雷达）
│   └── 痛点归因模型（问题分类 × 空间 × 时段）
└── 应用层
    ├── 概览仪表盘
    ├── 用户画像中心
    ├── 需求洞察雷达
    ├── 痛点地图
    ├── 调研方法工具箱
    ├── 协作空间规划
    └── 建设规划与 OKR
```

### 3.3 详细功能说明

#### 3.3.1 概览仪表盘（Overview）

- **关键指标卡**：固定展示 4 个核心指标，帮助用户 3 秒内了解全局。
- **趋势图**：双 Y 轴图表，满意度用折线（左轴，0-100%），反馈条数用柱状（右轴）。
- **用户构成图**：甜甜圈图，中心显示"7 类 用户群体"，右侧配图例。

#### 3.3.2 用户画像中心（Personas）

- **卡片设计**：采用彩色头部条 + icon + 名称 + 占比进度条，强化视觉区分。
- **选中态**：选中卡片高亮边框，下方详情面板同步更新。
- **详情面板**：左右分栏，左侧展示动机/行为/痛点，右侧展示需求清单与用户原话。
- **设计原则**：每类用户都要有一句"真实感"的用户原话（quote），增强同理心。

#### 3.3.3 需求雷达（Radar）

- **七个维度**：自习空间、资源获取、协作讨论、文化活动、数字服务、环境舒适、参考咨询。
- **交互**：点击底部用户按钮切换雷达图，并与用户画像卡片联动。
- **视觉**：用半透明填充的多边形展示需求轮廓，便于对比不同用户差异。

#### 3.3.4 痛点地图（Pain Map）

- **痛点条形图**：按反馈比例排序，用颜色区分严重程度， hover 显示具体反馈条数。
- **空间热力图**：用 7 行（区域）× 6 列（时段）网格展示拥挤度，颜色从绿（空闲）到红（拥挤）。

#### 3.3.5 调研方法工具箱（Methods）

- **方法分类**：定量、定性、创新三类，每类用不同颜色标签区分。
- **问卷框架**：提供可直接复用的 6 大维度，方便团队快速启动调研。

#### 3.3.6 协作空间规划（Collaboration）

- **五层需求**：展示图书馆在协作服务上"已具备"与"待建设"的层次。
- **讨论间看板**：模拟一周预约状态，帮助规划者理解空间紧张程度。

#### 3.3.7 建设规划（Roadmap）

- **四阶段时间线**：基础摸底 → 深度洞察 → 共创验证 → 未来进化。
- **每阶段目标**：列出 3-4 项可交付成果与关键结果指标。
- **OKR 表**：5 个关键指标的当前值、目标值和完成时限。

## 4. 非功能需求

### 4.1 性能

| 指标 | 目标 |
|------|------|
| 首屏加载时间 | ≤ 2 秒（在常见网络环境下） |
| 图表渲染时间 | ≤ 300 毫秒 |
| 交互响应时间 | ≤ 100 毫秒 |

### 4.2 可访问性

- 图表需附带文字说明，确保色盲/色弱用户可理解。
- 按钮和交互元素需支持键盘导航。
- 关键对比度符合 WCAG 2.1 AA 标准。

### 4.3 可扩展性

- 数据层使用独立 `data.js`，未来可替换为 API 接口。
- 图表渲染逻辑独立封装，便于新增图表类型。
- 用户画像模型预留字段扩展（如新增用户类型、需求维度）。

### 4.4 数据安全与隐私

- 原型阶段不收集真实用户数据。
- 真实落地时：
  - 用户行为日志需脱敏处理；
  - 问卷数据需匿名化；
  - 访谈录音需获得知情同意并加密存储；
  - 用户画像不可用于歧视性服务定价。

### 4.5 兼容性

- 支持 Chrome、Edge、Firefox、Safari 最新两个主版本。
- 响应式适配，平板和手机端可正常浏览（优先桌面端）。

## 5. 数据需求

### 5.1 模拟数据说明

原型使用 `data.js` 中的模拟数据，数据结构和数值基于以下公开研究进行"合理推演"，**非真实统计值**：

- 武汉大学《图书情报知识》2024 年"数智时代图书馆用户需求变化研究"
- 北京大学信息管理系"基于多元服务需求的图书馆用户类型划分研究"（7,314 份问卷）
- 南京大学图书馆 2025 年度读者意见分析报告（359 条反馈）

### 5.2 未来真实数据源

| 数据类型 | 来源系统 | 用途 |
|---------|---------|------|
| 到馆行为 | 门禁系统 | 用户频次、停留时长、热门时段 |
| 借阅行为 | OPAC / ILS | 阅读偏好、学科分布、热门书目 |
| 空间使用 | 座位预约系统 / IoT 传感器 | 热力图、空间饱和度 |
| 数字资源 | 数据库日志 / COUNTER 报告 | 资源访问量、校外访问成功率 |
| 用户反馈 | OA 信箱 / 留言板 / 满意度问卷 | 痛点分类、满意度跟踪 |
| 定性研究 | 访谈记录 / 焦点小组纪要 | 深层动机、情感需求 |

### 5.3 数据模型扩展建议

未来落地时，建议将 `data.js` 替换为后端服务，关键数据模型包括：

```
Persona: { id, name, icon, color, percentage, ... }
RadarDimension: { id, name, description }
PainPoint: { id, name, category, severity, count, description }
HeatmapCell: { zone_id, time_slot, occupancy_score }
ResearchMethod: { id, type, name, description, tools[] }
RoadmapPhase: { phase, period, status, goals[], metric }
```

## 6. 关键用户流程

### 6.1 初次访问流程

```
进入首页 → 查看概览仪表盘（3 秒全局认知）
    ↓
点击「用户画像」 → 浏览 7 类用户 → 点击卡片查看详情
    ↓
点击「需求洞察」 → 切换不同用户 → 观察雷达差异
    ↓
点击「痛点地图」 → 定位最突出的问题 → 查看空间热力分布
    ↓
点击「建设规划」 → 了解解决路径 → 制定本馆行动计划
```

### 6.2 决策支持流程

```
馆长/主管进入 → 查看满意度趋势 → 识别下降趋势
    ↓
查看痛点分布 → 发现「数据库访问」占比最高
    ↓
下钻查看研究型用户画像 → 确认该群体受影响最大
    ↓
调取调研方法库 → 制定专项访谈计划
    ↓
制定改进方案 → 分配预算 → 跟踪 OKR 指标
```

## 9. 风险与应对

| 风险 | 影响 | 应对策略 |
|------|------|---------|
| 数据来源分散、质量不一 | 洞察失真 | 建立数据清洗规范，优先接入高可信系统 |
| 用户隐私与知情同意 | 合规风险 | 最小化采集、匿名化处理、明确授权 |
| 馆员数字化能力不足 | 产品使用率低 | 提供培训、模板化报告、降低使用门槛 |
| 用户需求变化快 | 画像过时 | 建立季度更新机制，持续滚动调研 |
| 与现有系统整合困难 | 落地周期长 | 采用渐进式接入，先手工导入再自动化 |

1. 是否需要支持多校区/多分支馆的独立视图与对比分析？

### 11.3 设计原则

- **以用户为中心**：所有图表和功能都指向"理解用户"，而非展示数据。
- **从洞察到行动**：每个模块末尾都应能推导出"下一步该做什么"。
- **真实感优先**：用户原话、真实比例、真实痛点，比炫技更重要。
- **渐进式落地**：MVP 先解决"看得见"的问题，再解决"自动化"的问题。
