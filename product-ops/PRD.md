# 产品需求文档（PRD）v2
## 用户洞察驱动的「软件运营工作台」

> 版本：v2.0（视角校正版）  
> 编写日期：2026-08-06  
> 适用角色：**软件运营者**（非图书馆决策方，但能直接改软件、搞运营、定流程，并可向上游提建议）

---

## 0. 为什么有 v2（视角校正说明）

v1 把产品定位成了"给图书馆馆长看的管理后台"，列了大量需要决策权限才能落地的需求（改数据库采购、改隔音、改硬件）。这与你的实际身份不符。

你是**软件的运营者**：你不直接拥有空间、数据库采购或硬件决策权，但你有三类别人没有的能力——

1. **能直接改软件**（配置、迭代、上线功能）
2. **能直接搞运营**（活动、推送、内容、社群）
3. **能直接定流程与规则**（预约策略、权限规则、黑名单）

再加上第四类**间接杠杆**：用数据把"软件改不了的事"打包成结构化建议，交给能改的人（IT、空间、采购、决策层）。

> **本版本的核心目标**：把"我是不是什么都做不了"这个问题，答复为"你手里的杠杆有四类"，并把之前那些"无能为力"的痛点，逐条翻译成你能执行的动作。

## 1. 产品概述

### 1.1 产品定位

一套面向**软件运营者**的用户洞察与运营工作台。它帮助运营者：
- 看清软件里七类用户各自怎么用、要什么；
- 把用户痛点翻译成"我能直接做什么"和"我该向谁提建议"；
- 用结构化建议单撬动上游（硬件/采购/空间）；
- 用持续运营节奏把影响力变成可量化的结果。

### 1.2 一句话价值

> 你不是决策方，但你是**唯一同时握着软件、运营、流程三把钥匙，还能向上游提需求的人**。这把"钥匙串"就是你的影响力。

### 1.3 产品边界

| 我能做的（核心） | 我不能直接做（用建议撬动） |
|----------------|------------------------|
| 软件功能配置与迭代 | 数据库采购与校外访问稳定性 |
| 内容与活动运营 | 建筑隔音与空间改造 |
| 流程规则定义 | 硬件设施与无障碍改造 |
| 用户反馈响应 | 资源采购预算分配 |
| 结构化建议单 | 远程权限的顶层开放决策 |

## 2. 目标用户与场景

### 2.1 角色

| 角色 | 在平台里做什么 |
|------|--------------|
| **软件运营者（你）** | 看仪表盘、做功能配置、搞运营、定流程、提建议单 |
| **产品/技术同事** | 接收"能直接做"的需求，排期迭代 |
| **上游相关方（IT/空间/采购/决策）** | 接收"建议单"，决定是否采纳 |

### 2.2 关键场景（User Story）

1. **场景 A：被吐槽"数据库登不上"**  
   作为运营者，我看到权限类反馈占 40%（最高）。我先在软件内做"权限状态看板 + 故障自助排查 + 到期推送"，把能接的接住；再把"校外访问稳定性"整理成建议单，附 40% 数据，提给 IT。

2. **场景 B：被吐槽"占座严重"**  
   这是我能直接闭环的：改预约规则、加续座提醒、超时释放、黑名单——全程在软件内完成，不需要任何人批准。

3. **场景 C：被吐槽"研讨间隔音差"**  
   软件改不了墙体，但我可以做"安静区/讨论区分区预约引导"缓解；同时把 27% 的空间噪音投诉整理成建议单，提给空间改造团队。

4. **场景 D：每周运营复盘**  
   看 DAU、功能使用率、推送打开率、反馈响应时长，定位"哪些功能被冷落"，决定下周运营重点。

## 3. 功能需求

### 3.1 我的四类杠杆（核心模块）

这是整个产品的"骨架"，直接回答"我能做什么"：

| 杠杆 | 我能直接做的 | 平台如何支撑 |
|------|------------|------------|
| ⚙️ 软件功能 | 配置/迭代/上线功能 | 功能开关、配置面板、A/B 实验 |
| 📣 内容与运营 | 活动/推送/社群/书单 | 推送中心、活动日历、推荐位 |
| 📋 流程与规则 | 预约/权限/黑名单策略 | 规则引擎、策略配置 |
| 💡 建议与影响 | 向上游提结构化需求 | 建议单模板、数据依据自动填充 |

### 3.2 功能清单（优先级）

| 模块 | 功能点 | 优先级 | 说明 |
|------|--------|--------|------|
| 概览 | 我的四类杠杆总览 | P0 | 首页即回答"我能做什么" |
| 概览 | 运营 KPI（DAU/使用率/打开率/NPS） | P0 | 软件运营健康度 |
| 概览 | 运营趋势图 | P0 | NPS 与功能使用率走势 |
| 用户画像 | 七类用户（软件视角） | P0 | 重点：在软件里怎么表现 |
| 用户画像 | 每类"我能做的动作" | P0 | 直接可执行清单 |
| 痛点→动作 | 痛点映射到软件动作 + 建议 | P0 | 核心翻译器 |
| 建议清单 | 影响 Backlog 表 | P0 | 结构化向上游提需求 |
| 运营节奏 | 日/周/月/季动作 | P1 | 把影响力拆成节奏 |
| 运营方法 | 研究方法库（软件/运营/影响） | P1 | 持续获得洞察 |
| 成功指标 | 运营 OKR 表 | P1 | 量化影响力结果 |

### 3.3 核心功能：痛点 → 我的动作（翻译器）

这是 v2 最具价值的设计。每条用户痛点都被拆成两栏：

- **🔧 我能直接做的软件动作**（归到某一类杠杆，运营者独立可执行）
- **💡 需要向上游提的建议**（附数据依据，交给能改的人）

示例：

| 痛点 | 我能做的软件动作 | 向上游的建议 |
|------|----------------|------------|
| 数据库权限 40% | 权限看板、自助排查、到期推送、一键工单 | 提 IT：稳定性（附 40% 数据） |
| 空间噪音 27% | 安静/讨论区分区预约引导 | 提空间：隔音改造（附 27% 数据） |
| 占座 18% | 预约优化、续座、超时释放、黑名单 | —（软件内闭环） |
| 设施 12% | 报修入口、故障位置标注 | 提物业：维护清单 |
| 资源 8% | 荐购入口、需求榜、专题 | 提采购：增补（附需求榜） |
| 校友 10% | 数字卡申请流、权限透明化 | 提决策：远程开放 |

## 4. 非功能需求

| 维度 | 要求 |
|------|------|
| 性能 | 看板首屏 ≤ 2s，配置变更即时生效 |
| 可配置 | 功能开关、规则参数运营者可自助调整，无需发版 |
| 可审计 | 建议单状态（待提/已提/已采纳/已拒）可追溯 |
| 隐私 | 用户行为数据脱敏，反馈匿名化 |
| 兼容性 | 桌面优先，移动端可浏览 |

| 数据 | 来源 | 运营者角色 |

## 6. 关键流程

### 6.1 痛点处理流程（你每天在用）

```
收到反馈 → 归入痛点类别 → 判断杠杆归属
   ├─ 软件功能/内容/流程 → 我直接做（配置/迭代/运营）
   └─ 硬件/采购/空间    → 生成建议单（附数据）→ 提给上游
```

### 6.2 建议单流程（你的影响力出口）

```
发现软件无解的痛点 → 提取数据依据 → 指定影响对象 → 定优先级
   → 提交建议单 → 跟踪状态（待提/已提/已采纳/已拒）→ 复盘效果
```

## 9. 风险与应对

| 风险 | 应对 |
|------|------|
| 上游不采纳建议 | 用占比/热力图数据增强说服力；从小成本试点切入 |
| 功能迭代排期被压 | 优先做"软件内可闭环"的痛点（占座/流程） |
| 运营精力分散 | 用日/周/月/季节奏固化动作，避免忙乱 |
| 数据口径不一致 | 建立统一埋点与标签体系 |

## 10. 开放问题（待你确认）

1. 你具体运营的是什么软件？（阅读 App / 空间预约 / 图书馆系统 / 知识社区？）——这决定"软件功能"杠杆的具体范围。
2. 你向上游提建议的实际通道是什么？（周报 / 评审会 / 工单系统？）——决定建议单怎么"发出去"。
3. 你目前能直接改软件到什么程度？（全权配置 / 提需求给技术 / 只能内容运营？）
4. 是否已经有埋点或反馈数据？还是从零开始？
5. 这个工作台是给你自己用，还是要给团队/上级看？
